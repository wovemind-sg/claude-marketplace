# OpenFeature troubleshooting: symptom → cause → fix

Language-specific detail lives in `go.md`, `dotnet.md`, `python.md` (each has a "Gotchas" section). This file is the cross-language triage table plus a debug checklist. Verified against go-sdk 1.18.0, dotnet-sdk 2.14.1, python-sdk 0.10.0 and the spec snapshot of 2026-09-21.

## Debug checklist (do this first)

1. **Read the details, not the value.** Switch the call to the `*Details` variant and print `reason`, `errorCode`, `errorMessage`, `variant`, `flagMetadata`. Everything below keys off those two fields.
2. **Attach the SDK's `LoggingHook` at debug level** (Go `hooks.NewLoggingHook(false, logger)`, .NET `new LoggingHook(logger)`, Python `LoggingHook()`; JS/Java have equivalents). The SDK is silent by default (spec: no logging during evaluation), so without the hook you see nothing.
3. **Check provider state**: Go `client.State()`, .NET `client.ProviderStatus` / `Api.GetProviderStatus()`, Python `api.get_provider_metadata()` + a `PROVIDER_ERROR` handler. Subscribe to `PROVIDER_ERROR` and log `event_details.message`.
4. **Confirm which provider the client actually uses**: named-domain clients with no matching named provider fall back to the default provider *silently* in every SDK. A typo in the domain string is a common cause of "wrong backend".
5. **Confirm the provider is talking to the right backend/environment** with the backend's own tooling (flagd: `curl :8016/ofrep/v1/evaluate/flags/<key>`; OFREP backends: same path on their host; vendors: their dashboard "evaluation log").
6. **Reproduce with the in-memory provider.** If the in-memory provider returns the expected variant, the problem is in the provider/backend, not in your code or hooks.

## Symptom table

| Symptom | `reason` / `errorCode` | Cause | Fix |
| --- | --- | --- | --- |
| Every flag returns the code default right after startup | `ERROR` / `PROVIDER_NOT_READY` | Provider registration is asynchronous; you evaluated before init finished | Go `SetProviderAndWait`; .NET `await Api.Instance.SetProviderAsync(...)` or let `AddOpenFeature`'s hosted lifecycle run before serving; Python `set_provider_and_wait` (since 0.10.0 `set_provider` no longer blocks); JS `await OpenFeature.setProviderAndWait(...)`; Java `setProviderAndWait`. Or gate on the `PROVIDER_READY` event. |
| Defaults forever, no error logged | `ERROR` / `PROVIDER_NOT_READY` or `GENERAL` | Provider init failed and the SDK swallowed it (.NET `SetProviderAsync` catches `InitializeAsync` exceptions; Go `SetProvider` returns nil and reports via event; Python `set_provider` runs init in a background thread) | Use the blocking/awaiting form *and* register a `PROVIDER_ERROR` handler that logs `message`. Check credentials/URL of the backend. |
| Default returned, no error | `DEFAULT` | Flag exists, is enabled, but no targeting rule matched, so the backend's default variant applied. This is **not** an error. | Verify the evaluation context you send (targeting key, attribute names/case, types). Compare with the backend's rule. |
| Default returned, no error | `DISABLED` | Flag disabled in the backend. Some SDKs/providers return the *caller's* default here (.NET `InMemoryProvider`), others the backend default variant | Enable the flag or accept the default. Not an error by spec design. |
| Default returned | `ERROR` / `FLAG_NOT_FOUND` | Key typo, wrong environment/project/flag set in the provider config, provider bound to the wrong domain, or provider scoped by selector (flagd `flagSetId`) | Check the exact key in the backend; check provider env/config; for flagd see the `flagd` skill (selectors). |
| Default returned | `ERROR` / `TYPE_MISMATCH` | Getter type ≠ flag type. Classic cases: int flag read with float getter (Python is strict: `1` fails `get_float_value`, `1.0` fails `get_integer_value`, `True` fails `get_integer_value`), string `"true"` read as boolean, object flag read as string | Use the getter matching the backend's flag type. For JSON/object flags: Go `Object`, .NET `GetObjectValueAsync` (returns `Value`), Python `get_object_value` (dict/list). |
| Default returned | `ERROR` / `TARGETING_KEY_MISSING` | Provider requires a targeting key (fractional rollout / per-user rules) and context had none | Set `targetingKey` (Go `NewEvaluationContext(key, attrs)`, .NET `SetTargetingKey`, Python `EvaluationContext(targeting_key=...)`). Put it in transaction context for request-scoped code. |
| Default returned | `ERROR` / `INVALID_CONTEXT` | Context attribute type the provider cannot serialize (circular structure, non-JSON value, wrong nesting) | Keep attributes to string/number/bool/datetime/flat structures; avoid circular references. |
| Default returned | `ERROR` / `PARSE_ERROR` | Provider could not parse flag configuration (bad JSON/YAML in a file/HTTP source), or (Go) flag key is not valid UTF-8 | Validate the flag source with the backend's schema/validator. |
| Default returned | `ERROR` / `PROVIDER_FATAL` | Provider hit an irrecoverable error (e.g. bad credentials) and moved to `FATAL`; SDK short-circuits without calling it | Fix config, re-register the provider (Go `SetProviderAndWait`, .NET `SetProviderAsync`, Python `set_provider_and_wait`). |
| Percentage rollout flips between requests for the same user | `SPLIT` / `TARGETING_MATCH` | No stable `targetingKey` (missing, random per request, or different attribute per service) | Use the same stable id everywhere (user id/session id). Do not use email if another service uses id. |
| Rollout gives 100% or 0% instead of N% | `SPLIT` | All requests share one targeting key (e.g. hostname or a constant) | Pass the per-subject key in invocation/transaction context, not API-level context. |
| Context values I set are ignored | any | Merge precedence: API < transaction < client < invocation < before-hooks (spec 3.2.3); a higher level overwrote your key. Note .NET merges client *before* transaction (transaction wins over client) | Inspect the merged context in a `before` hook (`hookContext.EvaluationContext`) and move the value to the right level. |
| Transaction context never applies | any | No propagator installed (Python: `api.set_transaction_context_propagator(ContextVarsTransactionContextPropagator())`; .NET: `Api.Instance.SetTransactionContextPropagator(new AsyncLocalTransactionContextPropagator())` — default is no-op); Go: you passed a `context.Context` that did not come from `openfeature.WithTransactionContext` | Install the propagator once at startup; in Go thread the returned `ctx` through to the evaluation call. |
| `.NET`: `Api.Instance.GetClient()` returns no-op values in an app wired with `AddOpenFeature` | `ERROR` / `PROVIDER_NOT_READY` or `DEFAULT` | Since 2.14 `AddOpenFeature` registers an *isolated* `Api`; `Api.Instance` is a different, unconfigured API | Inject `IFeatureClient` (scoped) or `Api`; never mix the two. Same for `Api.Instance.SetTransactionContextPropagator` — call it on the injected `Api`. |
| `.NET`: `InvalidOperationException` when setting a provider | n/a | Same provider instance bound to two `Api` instances (global + isolated, or two tests) | Create a new provider instance per `Api`; `ShutdownAsync` unbinds. |
| `.NET`: `ArgumentException("Invalid value type")` on object flags | n/a | `new Value(myPoco)` — `Value` only wraps primitives, `Structure`, lists, `DateTime` | Build with `Structure.Builder().Set(...)`; deserialize via System.Text.Json (`ValueJsonConverter`) to a POCO. |
| `.NET`: hooks/events registered but nothing happens | n/a | `AddHook<T>()` twice with the same type name keeps only the first (keyed singleton); `AddContext` context is per-scope, not global | Give distinct hooks distinct names; use `api.SetContext` for global context. |
| Go: `errors.As(err, &openfeature.ResolutionError{})` never matches | n/a | Provider errors are rewrapped as `fmt.Errorf("error code: %w", errors.New(...))`; only `ProviderNotReadyError`/`ProviderFatalError` sentinels survive | Switch on `details.ErrorCode` instead of unwrapping the error. |
| Go: `RemoveHandler` does not remove | n/a | `EventCallback` is `*func(EventDetails)`; you passed a different pointer | Keep the callback in a variable and pass `&cb` to both Add and Remove. |
| Go: flags all default after a test | n/a | `openfeature.Shutdown()` resets the entire API (providers, hooks, handlers, context) | Call `Shutdown()` only at process exit; re-register in tests, or use `isolated.NewAPI()` per test. |
| Python: `client.set_evaluation_context` / `set_context` does not exist | n/a | Docs snippet is wrong; the client's context is an attribute | `client.context = EvaluationContext(...)` or `OpenFeatureClient(domain, version, context=...)`. |
| Python: `InMemoryFlag(state=DISABLED)` still resolves | n/a | `state` is never read by `resolve()` in 0.10.0 | Remove the flag from the dict or set `default_variant` to the off variant. |
| Python: `EnvVarProvider` boolean flag `"false"` evaluates `True` | n/a | Parsing is `bool(value)`, so any non-empty string is truthy | Use an unset variable for false, or another provider. |
| Python: event handler assertion fails in tests | n/a | Handlers run on a worker thread after `set_provider` returns | Wait on a `threading.Event` in the handler, or use `set_provider_and_wait` + `PROVIDER_READY` handler that was registered *before* setting the provider. |
| Python: `TypeError: unsupported operand type(s) for \|` on import | n/a | Python 3.9 unsupported since 0.9.0 | Python 3.10+. |
| Web/React: flag value stale after login | `CACHED`/`STATIC` | Static-context paradigm: context is set once on the API, provider must reconcile | `await OpenFeature.setContext({targetingKey: user.id, ...})`; listen for `PROVIDER_CONTEXT_CHANGED`/`PROVIDER_CONFIGURATION_CHANGED` (React hooks re-render automatically with default options). |
| Web: flag getter returns default in the first render | `ERROR` / `PROVIDER_NOT_READY` | Client SDKs evaluate synchronously against a cache filled asynchronously | Use React suspense hooks (`useSuspenseFlag`) or gate on `PROVIDER_READY`; give sensible defaults. |
| Hook side effect never runs | n/a | Hook implemented only `before` and an earlier `before` hook errored (remaining `before` hooks are skipped, spec 4.4.6), or hook registered on `Api.Instance` in a DI-isolated .NET app | Move telemetry to `after`/`finally`; register on the API instance actually in use. |
| Evaluation throws an exception | n/a | Not the SDK: your hook/provider code threw *outside* the SDK's catch (constructor, `Track` with empty event name in .NET, `ArgumentNullException` on null flag key) | Evaluation itself never throws for provider/hook errors (Requirement 1.4.10). Look at the stack for your own code. |
| Two backends needed at once (migration) | n/a | Trying to hand-roll fallback logic | Use domains (named client → named provider) or the multi-provider (`FirstMatch` default, `FirstSuccessful`, `Comparison`). See `concepts.md` §11 and the language files. |
| Values differ between two SDKs/languages for the same flag | n/a | Different evaluation context (attribute names, types, targeting key), different provider mode (RPC vs in-process), or a provider lagging behind spec | Diff the *merged* contexts via a `before` hook in both apps; check the provider READMEs for context transformation rules. |

## FAQ

- **Does OpenFeature store my flags?** No. It is an API + SDKs. You need a provider that talks to a backend: flagd (self-hosted, see the `flagd` skill), GO Feature Flag, Flipt, Unleash, a vendor (LaunchDarkly, ConfigCat, DevCycle, Split, PostHog, ...), the OFREP generic provider for any OFREP-speaking service, `env-var`/`in-memory` providers for simple cases.
- **Which provider should I pick for tests?** The in-memory provider shipped with every SDK (`memprovider`, `InMemoryProvider`, `InMemoryProvider`). It supports variants and context-based evaluators, no network.
- **Can one app use two flag backends?** Yes: domains (named providers + named clients) or the multi-provider.
- **Is `DISABLED` an error?** No. Spec defines a `DISABLED` reason, not an error code, because disabled flags are expected to be evaluated.
- **Why does the SDK not log errors?** By spec, evaluation is quiet; use the logging hook or a `PROVIDER_ERROR` handler.
- **Do I need a targeting key?** Only if the backend needs one (fractional rollouts, user overrides). Always sending a stable one is the safe default.
- **How do I know which spec version an SDK implements?** Badge at the top of the SDK README and https://openfeature.dev/docs/reference/sdks/sdk-compatibility .
- **Where do vendor-specific provider bugs go?** The vendor's repo if they host the provider; otherwise the language's `*-sdk-contrib` repo (see `resources.md`).
